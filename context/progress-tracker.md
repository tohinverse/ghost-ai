## Architecture Decisions

- shadcn was initialized with the `base-nova` preset (CLI v4.19), which uses `@base-ui/react` primitives instead of Radix. Composition uses a `render={<Component />}` prop, not Radix's `asChild`, on components like `Dialog`/`DialogTrigger`. Keep this in mind when composing shadcn primitives elsewhere in the app.
- `globals.css` defines the exact hex tokens from `ui-context.md` (`--bg-base`, `--text-primary`, `--accent-primary`, etc.) as the source of truth, then maps shadcn's semantic tokens (`--background`, `--primary`, `--border`, ...) onto them so `components/ui/*` render correctly unmodified. App-level code should prefer the UI-context Tailwind utility names (`bg-base`, `text-copy-primary`, `border-surface-border`, `text-brand`, `bg-accent-dim`, `text-ai`, etc.), exposed via `@theme inline` aliases.
- The app is dark-only: `.dark` is applied unconditionally on `<html>` in `app/layout.tsx` (no theme toggle), and `.dark`/`:root` token values are identical.
- `globals.css` previously defined `--font-sans: var(--font-sans)` (self-referential), so `body { @apply font-sans }` never resolved and the whole app rendered in the browser's serif default. Fixed during the auth phase by pointing `--font-sans`/`--font-heading` at `--font-geist-sans` and adding `--font-mono: var(--font-geist-mono)`, matching the fonts `app/layout.tsx` already loads. This is app-wide, not auth-specific.
- Clerk appearance is configured once on `ClerkProvider` in the root layout rather than per-component, so every Clerk surface (auth pages, `UserButton`, profile flows) inherits the same tokens. Clerk's `Variables` are typed as plain strings, so `var(--token)` values pass through and resolve at runtime.
- Route protection is deny-by-default in `proxy.ts`: everything not matched by the sign-in/sign-up matcher requires `auth.protect()`. New public routes must be added to that matcher explicitly.

- Project dialog state is shared through `ProjectDialogsProvider` (React context) rather than passed down as props from `EditorShell`. `app/editor/page.tsx` stays a server component, and a server component cannot pass a function child or callback props across the RSC boundary, so context is what lets server-rendered page content trigger a dialog the client shell owns. Any client component under the shell can call `useProjectDialogActions()`.
- `Project.isOwner` is the single flag gating item actions in the sidebar. Rename/delete render only for owned projects; the shared tab reuses the same `ProjectListItem` and simply gets no action menu. Replace this flag with the real owner/collaborator check once projects come from Prisma.
- `DialogContent` is given `rounded-3xl` (and `DialogFooter` `rounded-b-3xl`) at the call site in each dialog, instead of editing `components/ui/dialog.tsx`. This satisfies `ui-context.md`'s modal radius while leaving the protected shadcn foundation component untouched — resolves the open question from the editor-chrome phase.
- `DropdownMenuContent` from the shadcn base-nova registry sets `w-(--anchor-width)`, which sizes the menu to its trigger. Since the trigger here is a 28px icon button, the project actions menu passes `className="w-auto"` to override it. Expect the same override wherever a dropdown hangs off an icon button.

- The Prisma schema is multi-file: `prisma7.config.ts` sets `schema: "prisma/"`, so `prisma/schema.prisma` holds only the `generator`/`datasource` blocks and each domain gets its own file under `prisma/models/`. Add new models as new files there rather than growing `schema.prisma`.
- The generated client is emitted to `app/generated/prisma` (per the existing generator block) and is gitignored, so `npx prisma generate` is required after a fresh clone or any schema change. Import it as `@/app/generated/prisma/client`.
- `lib/prisma.ts` picks its connection strategy at runtime from the `DATABASE_URL` scheme rather than from a separate env flag, so the same code runs against a direct Postgres URL locally and a Prisma Postgres/Accelerate URL in deployment. The two branches produce different client types (the Accelerate branch is `$extends`ed), so the exported type is derived as `ReturnType<typeof createPrismaClient>` instead of being written as `PrismaClient`. `@prisma/extension-accelerate` had to be installed — the spec listed the other Prisma packages as already present but not this one, which the Accelerate branch requires.
- `Project.ownerId` stores the Clerk user ID as a plain `String`; there is no local `User` table, so Clerk remains the single source of identity. Collaborators are keyed by email rather than user ID, so an invite can exist before that person has signed up.

- API routes are excluded from `proxy.ts`'s blanket `auth.protect()` and enforce auth inside their own handlers instead. Clerk's `protect()` only redirects to sign-in for *page* requests (it sniffs `Sec-Fetch-Dest`/`Accept: text/html`); for a `fetch()` to `/api/*` it calls `notFound()`, which would have answered `404` where the spec requires `401`. Page routes are still deny-by-default; `/api/(.*)` is matched separately and skipped, and every API handler starts with a `getCurrentUserId()` check. Any new API route must do its own auth check — the proxy no longer covers it.
- Route handlers use the Next.js 16 `RouteContext<'/api/projects/[projectId]'>` global helper and `await ctx.params`, since `params` is a Promise in this version. `RouteContext` is only emitted by `next dev`/`next build`/`next typegen`, so a bare `npx tsc --noEmit` on a clean checkout fails until types are generated.
- Mutations distinguish "missing" from "not yours": the project is loaded first, so an unknown ID returns `404` and a real project owned by someone else returns `403`. This intentionally reveals that a project ID exists to a non-owner, which is what the spec's `403` requirement asks for.
- `lib/prisma.ts` now applies `$extends(withAccelerate())` to *both* connection branches. Previously only the Accelerate branch was extended, making the exported type a union of two structurally different clients — TypeScript then refused to call `findMany`/`findUnique` ("no signatures compatible with each other") because Accelerate overloads reads with `cacheStrategy`. The extension is inert without an Accelerate URL, so extending both is the fix that keeps one callable client type. This surfaced only now because the Prisma phase never called a model method from typechecked app code.

- The editor home fetches through the data layer (`lib/projects.ts`) directly rather than `fetch`-ing its own `/api/projects` route. A server component calling its own HTTP endpoint would cost a round trip and force cookie forwarding for auth; the route handlers stay for client-side mutations. Both paths share the same query helpers, so the shapes cannot drift.
- The project ID *is* the Liveblocks room ID: `<slugified-name>-<6-char-suffix>`, generated client-side in `useProjectActions` when the create dialog opens and sent as `id` on `POST`. Generating it at open time (with the suffix held in its own state, not re-derived per keystroke) guarantees the ID the user previews is the one persisted. `types/project.ts`'s `slug` is therefore display-only and equal to the ID.
- `lib/auth.ts` gained `getCurrentUserEmail()` because `ProjectCollaborator` is keyed by email, not user ID. Shared-project reads resolve through Clerk's primary email address; an account with no primary email simply sees an empty shared list rather than erroring.
- Delete distinguishes the open workspace from any other project via `useParams().projectId`, not by comparing against a prop, so the hook stays correct on both `/editor` (no param) and `/editor/[projectId]`.
- Prisma's unique-constraint failure is detected by duck-typing `error.code === "P2002"` (`isUniqueConstraintError`) rather than `instanceof PrismaClientKnownRequestError`, because `lib/prisma.ts` produces a different client build per connection branch.


- The share dialog's read-only mode is driven by an `isOwner` flag the *server* returns with the collaborator list, not by the client comparing IDs. The client already knows which sidebar list a project came from, but that flag describes the sidebar's view, not the request the API will authorize; returning it with the data keeps what renders and what the server permits in one answer. `GET` is deliberately member-readable (the spec gives collaborators a view of the list) while `POST`/`DELETE` are owner-only.
- Collaborator emails are normalized to lowercase (`normalizeEmail`) on the way in, and Clerk profile lookups are keyed the same way. `ProjectCollaborator.email` is compared against Clerk's primary address in `hasProjectAccess` and `listProjectsForCollaborator`, so a mixed-case invite would otherwise silently never match. Existing rows predating this were only ever created by tests.
- Clerk enrichment is best-effort and never fails the request: `getCollaboratorProfiles` catches everything and returns an empty map, so a Clerk outage degrades the dialog to emails-only rather than breaking the list. It also maps *every* address on a Clerk account, not just the primary, so an invite sent to someone's secondary address still resolves their name and avatar.
- Collaborator avatars use a plain `<img>` with an eslint exception rather than `next/image`. Clerk serves them from its own CDN, which would need to be added to `next.config` `images.remotePatterns`; at a 32px avatar the optimization is not worth coupling the config to Clerk's asset host.
- Removal is looked up with `findCollaboratorInProject(projectId, collaboratorId)` rather than by row ID alone. Ownership is checked against the project in the path, so a bare row lookup would let an owner delete a collaborator row belonging to a different project by pairing their own project ID with a foreign row ID.
- `useShareProject` fetches the collaborator list when the dialog opens rather than with the page. Sharing is occasional and the fetch costs a Clerk round trip per open, so paying it on every workspace load would be wasted work. The form is reset on *close* (in the dialog's close handler) rather than in an effect watching `isOpen` — `react-hooks/set-state-in-effect` rejects the effect form, and the close handler is where the state change actually belongs.

- Access control for the workspace route lives in `lib/project-access.ts`, not in the page. `getCurrentIdentity()` bundles the Clerk user ID with the primary email because the two membership checks are keyed differently — `Project.ownerId` by user ID, `ProjectCollaborator` by email — and both are needed for one decision. `hasProjectAccess` queries the collaborator row directly through the `projectId_email` compound unique rather than reusing `listProjectsForCollaborator`, which would fetch every shared project to answer a single yes/no. The same helper is what the future Liveblocks token route should gate on, per `architecture-context.md`.
- A missing project and an unauthorized one render the identical `AccessDenied` page. This is a deliberate reversal of the previous phase's `notFound()` for non-members: the spec requires `AccessDenied` for both, and rendering them identically also stops the page from confirming that an unknown project ID exists.
- `WorkspaceShell` is a sibling of `EditorShell`, not a replacement. The editor home has no project, so it has no navbar title, no AI sidebar, and no canvas; forcing one component to cover both would mean every workspace-only prop becoming optional and conditionally rendered. `EditorNavbar` is the one piece genuinely shared, so it takes optional `projectName`/AI-toggle props and renders neither on `/editor`.
- The active-room highlight is read inside `ProjectListItem` via `useParams().projectId` rather than passed down from the shell. This matches how `useProjectActions` already detects the open workspace and keeps the highlight correct on `/editor`, where there is no param and nothing highlights.
- Composing `Button` with a `Link` requires `nativeButton={false}`. The base-nova `ButtonPrimitive` assumes a native `<button>` and logs an accessibility error when `render` supplies an anchor. This applies to every future button-styled link, not just `AccessDenied`.
